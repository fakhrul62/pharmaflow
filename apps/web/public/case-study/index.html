The workflow problem

A pharmacy team needs to see which items are running low, identify expiring batches, receive supplier orders, and complete sales without losing track of stock. I rebuilt the reference template's page and workflow structure around those connected tasks, adding a transactional API and persistent data.

See what needs attention

Low stock and expiry alerts link directly to inventory views. Batch eligibility is checked again at checkout.

Keep the counter moving

Search or scan medicine barcodes, hold a complete sale draft, record payment, and print a receipt.

Keep changes accountable

Role permissions, audit history and database transactions protect stock and financial records.

What I built

A new interface and component system, a React/Vite application, and a NestJS/PostgreSQL backend. The implementation includes session authentication, server permissions, validated forms, batch stock allocation, prescriptions, receiving, returns, finance records, reports and responsive layouts. OpenAI Codex assisted development and review.

Design decisions

  • A restrained teal palette, readable tables and consistent forms keep operational tasks familiar.
  • Lazy routes separate checkout and reporting code; the API stores monetary values as integer minor units.
  • Server transactions commit inventory and financial effects together. Checkout rejects expired stock, oversells and invalid prescription dispensing.
  • Keyboard search, dialog focus handling and responsive layouts support daily use across desktop and smaller screens.

Verification and boundaries

The original implementation passed 102 backend integration assertions, four frontend unit tests and 11 browser tests. Release checks and CI are documented in the repository. The public demo is an expiring, read-only fictional preview; the full local app uses the real API and database.

Payments are recorded rather than charged. This is a single-pharmacy portfolio project. Full operational snapshots, JSONB domain records and a global transaction lock are practical demo choices; larger deployments need paged queries, typed domain tables, server aggregates and narrower transaction scopes.
